# Microduck 复刻全能工作台：解决方案设计

状态：已审核；阶段 0/1 已开始实现  
日期：2026-09-12  
范围：只做方案设计；本阶段不修改现有代码、不改变机器人运行时行为。

## 1. 目标与判断

### 目标

为当前 Microduck 复刻工作建立一个本地优先的“复刻工作台”（暂名
`Microduck Replication Workbench`），把已经存在的代码、训练仓库、硬件资料、命令、实验记录和真机验证串成一条可恢复、可追溯、可复用的工作流。

核心结果不是再写一套机器人控制系统，而是让复刻者能够回答这 5 个问题：

1. 我现在处于哪一个阶段，下一步是什么？
2. 我的电脑、训练环境、板卡和依赖是否满足前置条件？
3. 这一次运行使用了哪一个仓库版本、参数、模型和命令？
4. 失败发生在哪一层，下一条安全的排查命令是什么？
5. 这个模型/配置/硬件是否已经通过仿真、部署和真机验收？

### 当前根因

仓库已有能力不少，但分布在不同位置：

- Rust workspace 已有 `robotd`、`updaterd`、`configd`、`btd`、`mediad`、`robotctl` 和统一 IPC；
- `docs/design/` 记录了服务边界、安全、更新和远程链路；
- `docs/course/`、`docs/deep-dive/` 和 `docs/microduck-30day/` 已有学习路线、源码地图、实验模板；
- `tools/microduck_learning/` 已有配置查看、TensorBoard 分析和训练 smoke test；
- `scripts/` 已有板卡安装、部署、NPU、GStreamer、网络和测试脚本；
- `duck-whatled/` 已有学习资料的静态发布能力。

缺口是编排和证据链，而不是缺少另一个 daemon。当前最容易出现的失败是：路径不一致、依赖没有预检、命令靠手抄、实验参数没有锁定、日志和模型无法对应、部署前没有硬件门槛、失败后不知道该回滚还是继续。

### 推荐判断

推荐建设“本地优先的复刻工作台”：浏览器界面 + 本机编排服务 + 可复用 CLI。先服务单人、单项目、单机器人，不先做云端协作、应用市场、自动机械设计或大模型自动操控。

原因：

- 训练数据、模型、日志、CAD 和密钥体积大且敏感，本地更可靠；
- 真实机器人需要在局域网、SSH、BLE 和 Unix socket 之间切换，云端不是第一依赖；
- 现有 Rust/脚本资产可以直接被调用，避免重写；
- 工作台可以在没有真机时使用，真机接入只是一个适配器；
- 后续需要时可以把“报告、模板、实验结果”同步到云端，而不改变核心流程。

## 2. 边界

### 首版必须做

- 复刻项目创建、路径和版本登记；
- 环境预检和缺失依赖的可执行提示；
- 复刻阶段任务图和依赖阻塞；
- 对现有 smoke test、配置检查、构建、部署和健康检查命令做安全编排；
- 记录命令、工作目录、环境摘要、退出码、日志、产物和校验值；
- 从 TensorBoard、ONNX、manifest、`robotctl health` 生成可读结果；
- 失败分类和下一步排查建议；
- 生成可导出的 Markdown/JSON 复刻报告；
- 任何有风险的操作（扭矩、重启、刷写、更新、回滚、删文件）都要显式确认。

### 首版明确不做

- 不重写 `robotd` 控制回路、策略推理、安全层或 OTA；
- 不绕过 `robotd` 直接发送舵机/电机写入；
- 不在工作台内实现新的物理仿真或强化学习算法；
- 不自动生成未经验证的 CAD、BOM 或电路设计；
- 不默认上传摄像头、麦克风、训练日志或用户密钥；
- 不引入必须联网才能工作的账号体系；
- 不把外部仓库代码复制进当前仓库；
- 不把“1:1 复刻”当成无证据结论，许可证和来源始终单独记录。

## 3. 用户与核心场景

### 主要用户

首版只服务一个人或一个小团队中的操作者：懂基本命令行、但不想反复记住多个仓库和脚本的复刻者。开发者、硬件调试者和课程学习者共享同一套项目状态，权限和视图可后续拆分。

### 三条必须打通的路径

#### A. 从零到第一次可重复仿真

```text
新建项目 → 登记训练仓库/基线 commit → 环境预检
→ 运行官方策略或 CPU smoke test → 解析日志/曲线
→ 保存 checkpoint、ONNX、配置快照和结论
```

#### B. 从代码到板卡健康

```text
交叉编译/打包 → 预部署检查 → 通过 SSH/BLE/robotctl 安装
→ 更新 health gate → 失败则提示回滚路径
→ 记录 board serial、运行版本、健康结果和日志
```

#### C. 从硬件装配到可训练数据

```text
BOM/装配清单 → 供电与安全门槛 → 舵机 ID/方向/限位
→ IMU/相机/NPU/网络检查 → 保存校准参数
→ 允许进入策略部署或重新训练
```

任何一条路径都可以暂停、重启应用后继续，并显示阻塞项，而不是要求重头开始。

## 4. 产品形态

### 推荐形态

本地应用分三层，但首版尽量少进程：

```text
浏览器 UI（本机 localhost）
          │ HTTP/WebSocket 或本地 IPC
本机编排服务（项目、任务、执行、证据、权限）
          │ 适配器
现有 CLI / 脚本 / robotctl / duckctl / SSH / 文件系统
          │
本机训练环境、外部 microduck_rl、Radxa 板卡、真实机器人
```

推荐先做“本地服务 + 浏览器界面”，之后如需双击启动再封装为桌面壳（Tauri 或同类方案）。这样 UI 不绑定某个桌面系统，Windows/macOS/Linux 都能工作，也不会在第一版就引入一套重量级桌面框架。

### 备选方案与排除

| 方案 | 结论 | 原因 | 何时重新考虑 |
|---|---|---|---|
| 纯云端 SaaS | 首版排除 | 真机、密钥、模型和离线能力受网络影响，成本与隐私风险高 | 多人协作和远程实验成为主要需求 |
| 纯 CLI | 作为底层保留 | 最稳、最容易测试，但无法把阶段、证据和阻塞项形成统一视图 | 只需要自动化流水线、不需要图形化引导 |
| 本地服务 + 浏览器 UI | 推荐 | 复用现有命令和协议，跨平台，风险可控 | 默认方案 |
| 直接做大型桌面客户端 | 延后 | UI、安装、自动更新和跨平台负担会遮蔽真正的复刻问题 | MVP 工作流已稳定，用户确实需要离线桌面体验 |

## 5. 功能模块

### 5.1 项目与基线

- 创建项目：选择当前仓库、`microduck_rl`、可选 OpenMicroDuck/CAD/语音仓路径；
- 记录每个来源的 URL、本地路径、分支/commit、许可证状态和最后扫描时间；
- 一键生成“基线快照”：Git commit、Rust/Python/uv/CUDA/系统摘要、工具版本；
- 明确区分当前工作树、已提交版本和外部仓库，不执行隐式 `reset`、`clean` 或覆盖。

### 5.2 任务图与阶段看板

初始阶段固定为：

1. 认识项目与许可证；
2. 开发机和训练环境；
3. 源码阅读与协议对齐；
4. 机械/电路/BOM；
5. 仿真与 smoke test；
6. 板卡、舵机、IMU、相机和 NPU bring-up；
7. ONNX/运行时/部署；
8. 真机验收与迭代。

每个任务拥有：前置任务、执行方式、是否只读、风险等级、预期产物、成功判据、失败建议和人工确认点。状态使用 `未开始 / 可执行 / 运行中 / 成功 / 失败 / 阻塞 / 需人工`，不把“命令退出 0”直接等同于“复刻成功”。

### 5.3 环境预检

分三类显示结果：

- 本机：Git、Rust 1.89、Cargo、Python/uv、Node（如需要）、GPU/CUDA、Docker、磁盘和权限；
- 训练：训练仓是否存在、依赖是否已同步、任务是否注册、smoke test 是否可 dry-run；
- 板卡：SSH 可达、架构、系统版本、磁盘、电源/温度、服务版本、`robotctl health`、模型和运行时依赖。

预检输出必须包括“为什么检查、当前值、要求值、修复命令、是否会改变系统”。缺依赖只给可复制命令，不在首版偷偷安装系统包。

### 5.4 源码地图与文档导航

复用现有 `docs/microduck-30day/source-map.md`、课程和 deep-dive 文档，不再复制一套知识库。

- 按目标筛选：看懂控制链、调 observation/reward、改参数、部署 ONNX、调舵机、排错；
- 展示文档 → 源文件 → 命令 → 产物的关联；
- 支持在结果中附上文件路径和行号；
- 外部资料标注来源和许可证，不把网络内容当成本地事实。

### 5.5 仿真、训练与模型验证

- 调用现有 `setup_simulation`/训练仓库和 `run_5_iteration_smoke.sh`，首版只做编排；
- 所有运行先生成 dry-run 命令和工作目录；
- 记录环境数、steps、iterations、GPU、run name、日志目录和 commit；
- 解析 TensorBoard scalar，生成曲线和摘要；
- 检查 ONNX 输入/输出形状、模型 API、manifest 和校验值；
- 清楚显示“流水线跑通”和“策略学会走路”是两个不同结论；
- 支持用户手动标注假设、变量、基线、结果和下一步，复用已有实验模板。

### 5.6 硬件与校准

首版以清单和证据为主，避免自动乱动硬件：

- BOM：部件、规格、数量、来源、替代件、价格、到货状态；
- 装配：步骤、图片/文件、人工确认、风险提示；
- 台架：供电、电压、电流、共地、舵机 ID、方向、限位和温升；
- 传感器：IMU、相机、ToF、NPU、网络和存储；
- 校准：原始值、参数、操作者、时间、工具版本和回滚文件；
- 每个危险操作前显示“会让哪个部件动作、如何急停、失败如何恢复”。

### 5.7 部署、健康和恢复

- 优先调用 `robotctl`、现有部署脚本和 updaterd 的验证/回滚机制；
- 部署前检查目标板、release、签名、模型、磁盘、服务依赖和供电；
- 部署中显示阶段性进度，但不自行解释一个尚未完成的 update；
- 部署后同时读取软件和硬件健康，不用单一版本号代表全局状态；
- 失败时显示“保留现场 → 收集日志 → 回滚/重试”的顺序；
- 生成 support bundle：版本、配置摘要、最近日志、update history、模型 manifest，自动脱敏。

### 5.8 诊断助手

首版不做自由发挥的 AI 自动修复，采用可审计的规则匹配：

- 错误指纹：缺工具、路径不存在、shape 不匹配、模型 API 不一致、IPC 超时、板卡不健康、舵机无响应、依赖版本不兼容；
- 每个指纹关联证据来源、最小排查命令和禁止动作；
- 结果标注 `已证实 / 高概率 / 待验证`；
- 只有用户确认后才执行有写入或重启的命令。

后续可以接入本地/云端 LLM 做解释和检索，但不能让模型拥有越过安全层的执行权。

## 6. 建议的数据模型

首版使用一个本地项目目录保存小型元数据（SQLite 或同等轻量存储均可，最终以实现阶段评估为准），大文件仍放原路径或 artifact 目录，不复制模型和 CAD。

```text
Project
  id, name, root, created_at, schema_version
Source
  id, project_id, kind, path_or_url, commit, license_status
EnvironmentSnapshot
  id, project_id, host, tools, os, arch, gpu, captured_at
Task
  id, phase, title, deps, risk, status, check_definition
Run
  id, task_id, command, cwd, args, started_at, ended_at, exit_code, log_path
Artifact
  id, run_id, path, kind, sha256, size, metadata
HardwareUnit
  id, serial, board, firmware, connection, calibration_ref
Experiment
  id, hypothesis, variable, baseline, result, decision, evidence_refs
Evidence
  id, kind, path_or_uri, sha256, captured_at, redaction_status
```

所有运行和证据都带 `schema_version`，避免以后字段变化后无法读取旧项目。密钥不进入这些记录；需要连接板卡时使用系统凭据、临时会话或加密存储。

## 7. 安全与可靠性约束

1. 默认只读；写文件、安装依赖、重启、刷写、OTA、回滚、扭矩和舵机动作属于不同风险等级。
2. 命令使用参数数组，不用字符串拼接 shell；工作目录和可写路径必须显示。
3. 禁止隐式 `git reset --hard`、`git clean`、删除用户目录或覆盖未提交文件。
4. 日志、报告、support bundle 自动脱敏：Wi‑Fi、token、PIN、SSH 私钥、绝对路径中的用户信息可选择替换。
5. 真机控制始终经过 `robotd`/`robotctl`/既有 API；工作台没有原始电机写入接口。
6. 操作可中断、可重试、可恢复；每个写操作尽量先生成备份和 dry-run。
7. 任何“成功”结论都必须有证据引用；没有真机证据时标为“仿真通过”或“待验证”。
8. 外部资料、模型、CAD、图片和代码逐项记录来源与许可证，避免把“开源”误读为可商用或整机可复制。

## 8. MVP 实施顺序

### 阶段 0：协议与样例（约 3–5 个工作日）

- 固定项目元数据、任务状态、run/artifact/evidence schema；
- 为现有脚本定义 dry-run 和机器可读结果的最小契约；
- 选一条端到端黄金路径：环境预检 → 5 轮 smoke test → TensorBoard 摘要 → 报告；
- 以假执行器验证失败、取消、恢复和日志脱敏；
- 不接真机、不加 UI 复杂交互。

交付物：schema、CLI 入口、一个可重放的黄金路径、样例项目和验收记录。

### 阶段 1：本地 MVP（约 1–2 周）

- 项目创建/导入；
- 环境预检；
- 任务看板；
- dry-run/执行/取消/重试；
- 运行日志和 artifact 索引；
- Markdown/JSON 报告；
- 简单浏览器界面。

验收：在一台干净开发机上，从打开应用到生成一份带 commit、命令、曲线和结论的 smoke 报告不超过 30 分钟；重启应用后可继续，不改动外部训练源。

### 阶段 2：硬件与部署（约 2 周）

- SSH/板卡适配器；
- `robotctl health`、版本和 update history 汇总；
- 供电/舵机/IMU/相机/NPU 清单；
- 部署前检查、收集日志和回滚指引；
- support bundle 脱敏导出。

验收：没有连接真机时不会误报“硬件通过”；连接一台板卡时能区分“不可达、软件不健康、硬件不健康、版本不一致”。

### 阶段 3：实验与迭代（约 2 周）

- 实验模板、参数 diff、A/B 对比；
- TensorBoard/ONNX/manifest 关联；
- 源码地图和文档跳转；
- 失败指纹和规则诊断；
- 一键生成复盘报告。

验收：一次实验可以完整回答“改了什么、用哪个基线、产生什么产物、结果是什么、下一步做什么”。

### 阶段 4：可选增强（不纳入首版承诺）

- Tauri 桌面封装；
- 团队共享项目和评论；
- 浏览器内远程 WebRTC 监控；
- 本地模型辅助检索/解释；
- BOM 采购同步、价格跟踪、CAD 预览；
- 多机器人比较和策略/校准版本管理。

这些功能只有在首版指标稳定后再排期，否则会把“复刻成功率”问题重新变成“做了一个大平台”。

## 9. 验收指标

### 效率

- 从新建项目到第一次可重复 smoke test：≤ 30 分钟；
- 从失败日志到定位到一个明确下一步：≤ 5 分钟；
- 复刻者不需要手工拼接超过 3 个仓库路径或命令；
- 同一项目重跑时，commit、参数和产物可自动复用。

### 成功率与可追溯性

- 环境预检能在执行前拦住已知缺陷；
- 每次训练/部署运行都有命令、版本、日志和产物引用；
- 100% 的写操作在执行前显示影响范围并可取消；
- “仿真通过、模型通过、板卡健康、真机动作通过”四种结论不混淆；
- 失败后能保留现场，不因工具自动清理而丢证据。

### 安全

- 默认不开启电机动作和远程控制；
- 不把 Wi‑Fi、PIN、token 或 SSH 私钥写入普通日志；
- 不因工作台故障阻塞 `robotd`、`updaterd` 或既有恢复路径；
- 删除、重置和覆盖动作必须明确、可审计，优先可恢复操作。

## 10. 需要方案审核时确认的事项

默认建议如下；任何一项若不同，会改变实施顺序：

1. **首版定位**：先做复刻编排和验证工作台，不做新的机器人控制系统；
2. **运行形态**：本地服务 + 浏览器 UI，桌面封装延后；
3. **首条黄金路径**：环境预检 → 训练 smoke test → 指标分析 → 报告；
4. **真机范围**：第二阶段接入 SSH/`robotctl`，首版不自动驱动舵机；
5. **存储策略**：项目元数据本地保存，大模型/CAD/日志不复制、不默认上传；
6. **目标平台**：先支持当前开发机和 Linux/Radxa 部署路径，跨平台细节在 MVP 验收后补齐；
7. **名称**：暂名“复刻工作台”，确认后再固定产品名和仓库目录。

审核已按默认决策通过，当前先实现阶段 0/1 的本地闭环；真机接入前仍需重新确认硬件路线和安全边界，不把软件测试结果当作实机通过。

# HD-1910-C001 全链路落地手册

这份手册管的是**装机主线**：15 颗 HD-1910-C001 已经装进机身、Radxa Zero 3W 已经在跑、
躯干上有一颗 LSM6DSV16X，要把这套东西推到"可以松吊装、可以走"。它和
[HL-2915 手册](HL2915全链路落地手册.md)是两条独立路线，门槛编号也不同（这里用 H，那里用 S）。

```text
H0 线材与共地
  → H1 15 颗按官方 ID 在线
  → H2 总线持续健康
  → H3 IMU 独立有数据（舵机掉线也不瞎）
  → H4 界面上看得见 IMU
  → H5 15 个关节零位来自实测
  → H6 IMU 安装方向已核对
  → H7 舵机与 IMU 互相核对通过
  → H8 运动解锁，悬空可控
  → H9 模型来自这条链路自己的实测
```

不要把"程序能编译"当成"机器人能走"，也不要把"IMU 有数据"当成"IMU 装对了"。
每一层都有自己的通过条件；上一层没有通过，就不进入下一层。**H5 和 H6 谁先谁后不能换**，
理由见 §8。

## 1. 先看当前真实状态

### 已经在板子上或工作树里

- **两种 IMU 数据源，同一个解码契约。** `bus.imu_source` 是
  `Choice(&["ft6", "i2c_lsm6dsv16x"])`（`robotd-params/src/registry.rs`），默认 `Ft6`。
  两条路产出**同样的 12 字节 gyro/SFLP 载荷**，区别只是物理传输：`ft6` 是舵机总线上的
  ID=200 网桥，`i2c_lsm6dsv16x` 是直接读芯片、**不占用 ID 200**（`duck-control/src/imu_i2c.rs:1-4`）。
- **总线容错**：舵机不在线时 IMU 独立运行，phase 报 `servo_read_error`
  （`feetech_commissioning.rs:1300`，中控标签"舵机读取异常 · IMU 在线"）。舵机一旦应答，
  约 100 ms 内自动补做扭矩确认并转 `ready`，**不需要重启 robotd**。
- **中控 IMU 页**：`console/telemetry.py` 取数已带回退链——扩展帧 `extension.imu` →
  状态帧 `state.imu` → `safety.gravity`，来源标签随之显示
  `robot.state.diagnostics` / `robot.state.imu` / `robot.state.safety.gravity`。
  实测 46 Hz 实时。
- **标定门控三件套**：`motion_enabled`、`imu_mount_verified`、逐关节 `calibrated`，
  存在板上 `/etc/robot/feetech-ft5/hd1910-calibration.toml`；模板默认
  `motion_enabled = false`、`imu_mount_verified = false`、
  `imu_source = "ft6"`、`imu_mount_quat = [√½, 0, √½, 0]`。
- **关节 capture**：`feetech_commissioning.rs:326` 的 `capture()` 由"已知角度 + 方向"反解
  `zero_raw`，见 §7。
- `capture` 和 `verify-imu` 只有**中控**这一个入口（`console/service_control.py:94-95` →
  `/run/robotd.sock`）。主仓和 kissqy 的 `robotctl` 都**没有**对应子命令——不要去找一条
  不存在的命令行。

### 还不能宣称完成

- 上表的 I²C IMU、容错、中控显示都还没提交进任何仓库；**换一台机器就是换一套行为**。
- `imu_mount_verified` 需要机身刚性固定 IMU 之后实测，目前没有有效值。板上的
  `imu_mount_quat` 仍是官方默认，而官方默认对应的是**总线网板**的贴装朝向，
  不是你把一颗 LQ 模块用杜邦线挂在 I²C 排针上时的朝向。这两者不是一回事。
- 舵机↔IMU 的联合核对（H7）没有自动化，仍要人工执行与记录。
- 15 颗舵机的 `zero_raw` 若仍是默认 2048，那么**没有任何一个关节的零位是实测的**。

### 与主仓的差异（避免拿主仓的行为判断这条路线）

| 事实 | 主仓 | HD-1910 路线 |
|---|---|---|
| IMU 唯一来源 | 总线 ID=200 | ID=200 **或** I²C 直读，由 `bus.imu_source` 选 |
| 关节 ID | 台架用 1..15（`hl2915.rs`） | 官方 20–24 / 30–34 / 10–14 |
| 安装旋转 | 硬编码 `DEFAULT_MOUNT`，无参数键（`duck-control/src/imu.rs:78-83`） | `imu_mount_quat` 存在标定文件里，可由 `verify-imu` 写入并热生效 |
| 标定落点 | `robotd.toml` 的 `bus.hl2915_zero_raw/direction` | `hd1910-calibration.toml` 的逐关节记录 |

`docs/design/robotd-design.md` §8 把 **per-device IMU calibration（加计/陀螺零偏）**列为
明确延后——这一条**不要做**：融合在芯片 SFLP 里，陀螺零偏由 SFLP 自己估。本手册要做的只是
**安装朝向**，它是一个四元数，不是零偏。

## 3. H0–H2：整机接线与 15 颗在线

单只舵机的台架验证、URT2、电源选型、帧格式和寄存器速查都在
[URT2-HD1910 接线组装与测试指南](URT2-HD1910接线组装与测试指南.md)，
本次到货的 HAT 线材核对与整机接线步骤在
[1910-HAT 接线与标定清单](1910-HAT接线与标定清单.md) §1-§3。这里只写这一关独有的三件事。

**一、间距不是小事。** HAT 的舵机口是 JST EH 3P（B3B-EH-A，2.5 mm），舵机引出线端是
飞特 AMP2.0-3P（2.0 mm）。**间距不同，不能直插**，中间必须用两端各自匹配的转接线；
到货后两头分别试插，并逐根按功能核对针序，不要按颜色判断（三根全黑）。历史上这里已经
画错过一次（PR #12 曾把 HAT 侧画成 PH 2.0）。

**二、上电顺序。** 2S 电池经保险丝（台架 3–5 A）供舵机轨；Radxa 保持自己的供电，
**不从 HAT 取电**。⚠️ 严禁 7.4 V 碰 Radxa 任何引脚。

**三、ID 不对就单颗改，不要凑。** 若某颗不在线或 ID 不符：从 HAT 拔下这一颗，单独接
URT2（或 HAT 单口），出厂 ID1@1 Mbps → 改写官方 ID → REBOOT → 新 ID 验证 → 贴标，
**一次只接一只**。改完再回整机总线。

H2 的判据是"持续"，不是"跑通一次"。总线上任何一次抖动都会变成控制环里的一帧旧数据，
而旧数据在姿态和摔倒判定上比没数据更危险。

**H2 里"过流"这一项现在判不了，这是已知状态而不是 bug。** 标定文件里的
`units_verified = false` 和 `current_ma_per_count = 0.0` 是一对：未实测出每计数毫安系数之前，
`currents_ma` 被直接写成 **NaN**（`duck-control/src/feetech.rs:1416-1420`），遥测里的
`current_available` 为 false。所以 H2 阶段只能靠状态字、电压和温度三项把关；
要么你先按型号实测出这个系数并置 `units_verified = true`（此时它必须是正有限值，否则
`validate()` 拒绝配置），要么就把"过流保护"这一项记为**未生效**，不要在有 NaN 的情况下
声称过流已验证。

## 4. H3：IMU 来源怎么选

两颗都叫"IMU"的器件先分清：官方 Robot HAT 上的 **BMI088 走 I²C，由 `tofd` 读，步态闭环
不用它**；这里说的是**躯干**那颗 LSM6DSV16X——控制环和摔倒判定读的是它。

| 来源 | 怎么接 | 优点 | 代价 |
|---|---|---|---|
| `ft6` | LSM6DSV16X 焊在总线网桥上，作 ID=200 | 与官方架构一致；一条总线；一次 `sync_read` 顺带读完 | 多一块板和一个故障点；`i2c_probe` 不适用 |
| `i2c_lsm6dsv16x` | 模块 4 根线到 40-pin I²C | 少一块板；模块可以随便挪位置，适合先做标定 | 多一条独立总线；`robotd` 要单独开一次设备 |

选 `i2c_lsm6dsv16x` 需要四处同时一致，**少一处就会失败，而且失败方式各不相同**：

```toml
# /etc/robot/robotd.toml 的 [bus]
imu_source      = "i2c_lsm6dsv16x"
imu_i2c_device  = "/dev/i2c-pihat"
imu_i2c_address = 107          # 0x6b；本模块实测值，另一块板可能是 0x6a
```

1. **标定文件也必须同 `imu_source`**。`/etc/robot/feetech-ft5/hd1910-calibration.toml` 里
   要在 `imu_mount_quat` 旁边写 `imu_source = "i2c_lsm6dsv16x"`，否则 `robotd` 拒绝打开总线，
   报 `IMU source in calibration does not match ...`。这是有意的：姿态来源和安装四元数
   来自同一份标定，不允许一半新一半旧。
2. **systemd 要放行设备**。`DeviceAllow` 少一行时 `open()` 以 EPERM 失败。新打包
   （`packaging/runtime.py`）已带 `DeviceAllow=/dev/i2c-pihat rw`；**在此之前装的 robotd**
   需要手工把这行加进 `/etc/systemd/system/robotd.service.d/zzzz-r17-0151.conf`（或更晚的
   drop-in），再 `systemctl daemon-reload`。
3. **地址要实测，不要猜**。`i2cdetect -y <总线>` 扫到 0x6a 或 0x6b 才算接对。
4. **robotd 只在启动时打开总线一次**，之后停在 `configuration_error` 直到你重启它。
   所以顺序是：**先把舵机轨上电，再 `systemctl restart robotd`**。

改之前可以先用仓库自带的独立探针确认芯片本身没问题——它只碰选定的 I²C 设备，
完全不碰 robotd、舵机串口或 ID=200：

```bash
sudo python3 tools/imu_i2c_probe.py --bus /dev/i2c-pihat --address 0x6b --hz 50
```

它会校验 `WHO_AM_I=0x70`、配置 120 Hz 高性能模式、打开 SFLP game vector 与 FIFO、
等 1.5 s 收敛，并记录采样间隔、错过的时隙、I²C 错误、FIFO 溢出和完全重复的原始帧。
`0x6a`/`0x6b` 之外的地址参数会被直接拒绝。

**H3 判据**（拔舵机电源也要成立）：

```bash
ssh root@<板 IP> 'robotctl health'
# 总线详情：/run/robotd.sock 的 robot.busStatus
#   last_sample.imu.transport 应为 "i2c_lsm6dsv16x"
#   last_sample.imu 应带解码后的 gravity / gyro_rad_s / quaternion_wxyz
#   last_sample.servos 在舵机在线时应为 15 颗
```

`imu_ready` 的门槛是至少 **25 个有效四元数样本**（`duck-control/src/imu.rs:99-101`，约 0.25 s）；
就绪之前姿态是默认值而不是测量值，摔倒判定不允许在此之前运行。
`stale` 的定义是**连续字节完全相同的块**，冻结判据 `IMU_FROZEN_RUN = 25`（`bus.rs:78`）——
"读得到但一直是同一帧"比"读不到"更坏，因为它会一直给一个看似合理的旧姿态。

## 5. H4：界面上看 IMU

这一关的答案是"**能看，但只有中控能看全**"。四个界面各自的真实状态：

| 界面 | 躯干 IMU | 说明 |
|---|---|---|
| **kissqy 中控**（`console.py --feetech`） | ✅ 已有 | 陀螺、四元数、roll/pitch、状态徽标 `live`、来源标签；`imu_fresh` 不成立时置灰 |
| **`robotctl monitor`** | ❌ | 只画**手柄** IMU 的线框姿态（`robotctl/src/imu_view.rs`）；躯干 IMU 只在 `robotctl health` 里以 `ready`/stale 计数出现 |
| **WebRTC 控制台**（机器人自带网页） | ❌ | `robot.state` 从 v24 起就带 `imu: {gyro, quat}` 并以 50 Hz 推送（`duck-ipc-proto/src/lib.rs:3787,3803`），但 `mediad/webclient/index.html` 全文**一个 imu 字段都没渲染** |
| **microduck-studio** | ⚠️ 只有证据字段 | 硬件档案的 `imu.model`、探针解析出的 `imu_ready`/`stale_imu`/`max_stale_run`、标定卡里**手填**的 `imu.rpy_deg`（`visual-studio.js:169,284-288`，只进 SQLite、**从不下发机器人**） |

中控的起法（它只绑 127.0.0.1，为的是不把未认证的诊断数据暴露到局域网）：

```bash
# 板上或开发机
python3 Microduck-kissqy/microduck-hd1910/firmware/console/console.py \
  --feetech --ssh root@<板 IP>
# 浏览器访问前，本机开转发
ssh -L 8090:127.0.0.1:8090 root@<板 IP>
```

`--feetech` 模式**不直接占用串口**，它读的是 `/run/robotd.sock`——这一点对 H5/H6 至关重要：
同一时刻总线上只能有一个主站，中控标定时 `robotd` 独占总线，**Studio 的 URT2 调试台不要同时连**。

**待办一次**：如果 IMU 页的来源标签还是旧值、徽标不是 `live`、陀螺和四元数不亮，
先重启一次 `console.py` 并重新输入机器人密码——这是当前已知的一次性动作，不是故障。

若以后要把躯干姿态搬到 WebRTC 控制台或 Studio 上：渲染**已有**的 `robot.state.imu` 不需要改
IPC、不需要动 `permits()`、不需要 bump `API_VERSION`；一旦要**新增方法**，就必须同时改
`duck-ipc-proto` 的 `Call`、`mediad/src/route.rs`、`btd/src/route.rs` 三处，编译会故意失败提醒你。

## 6. H5：15 个关节的零位与方向

关节标定在中控的"关节标定"面板，操作顺序：

1. 面板显示 phase `ready`、扭矩 off、按钮解锁；
2. **RELAX 卸力** → 支撑机身 → 手动摆位到某个**你知道的角度**；
3. 逐关节 `capture`；
4. 缓慢驱动到机械限位两端，量取并填 `min_rad` / `max_rad`；
5. 保存 → 写 `/etc/robot/feetech-ft5/hd1910-calibration.toml`。

`capture()` 做的事（`feetech_commissioning.rs:326-360`）就一行数学：

```text
zero_raw = position_raw − direction × angle_deg / 360 × 4096
```

它在写入前会拒绝四种输入，这些拒绝是保护你的，不要绕：

- `direction` 不是 `±1`；
- `min_deg >= max_deg`，或已知角落在限位区间之外；
- 任一角度不是有限数；
- 算出的 `zero_raw` 落在 `0..4095` 之外——**这一条几乎总意味着 angle 或 direction 填反了**，
  此时正确的做法是重测，不是放宽校验。

还有三条不写在脸上就会踩的行为：

- **每次 capture 都会把 `motion_enabled` 打回 `false`**（`feetech_commissioning.rs:364`）。
  所以在 15 个关节没标完之前运动本来就开不了；不要在标到一半时去找"为什么动不了"。
- **输入用角度，存储用弧度。** 面板要的是 `min_deg`/`max_deg`（度），落盘是 `min_rad`/`max_rad`
  （官方关节弧度，`.to_radians()`）。手改 TOML 时填错单位不会报错，只会让限位差 57 倍。
- **限位两端会被再次验证**：`raw = zero_raw + direction × angle / 360 × 4096`，任一端超出
  `0..4095` 就报 `joint limits cross the single-turn encoder boundary`。这是 12-bit 单圈编码器
  的物理边界，越界的限位在真机上会撞圈。

三个必须记住的点：

- **2048 居中不是装配零位。** "回中"写的是舵机自己认为的中位，和机身装配后的关节零位
  是两件事。整组居中（`center`）只对**尚未装配**的舵机有意义，中控会硬性拒绝在未勾选
  `unassembled` 时执行。
- **已知角度要真的已知。** 用手量一个大概角度去 capture，得到的零位误差会直接进入策略观测，
  后面无论怎么调 P/D 都补不回来。用一个实际的定位块或量角器，并把它写进记录。
- **一处标定三端一致。** 同一份 `hd1910-calibration.toml` 之后会被训练台拉走烘进仿真，
  所以不要在有两条不同零位记录的情况下继续。

## 7. H6：IMU 安装方向核对与 `verify-imu`

**先决条件：模块必须刚性固定在躯干（`trunk_base`）上。** 杜邦线挂着、贴在会动的头上、
或者用双面胶带在可以转动的壳体上——任何一种都不允许点 `verify-imu`。理由有两个，都是硬的：

- 策略观测里的角速度和投影重力只取决于 IMU **固连刚体**的姿态。仿真把传感器绑在
  `trunk_base`；装在随颈关节转动的头上就是 sim-to-real 失配（`docs/deep-dive/43-imu_to_dxl使命.md`）。
- 安装方向属于**训练契约**：硬件贴装、代码 mount、重训数据三者必须同源，改任何一处都要
  留档（`docs/deep-dive/68-IMU与摄像头.md:37`）。

坐标系约定：躯干 `+X` 向前、`+Y` 向左、`+Z` 向上，正立时投影重力 `gravity = [0, 0, −1]`。
官方默认 mount 是绕 Y 的 +90°，把芯片读数旋到 `trunk = [+raw_z, +raw_y, −raw_x]`。

**五阶段实测**（判据沿用 [HL-2915 路线全流程教程](HL-2915路线全流程教程.md) §3.4，本手册不另立标准）：

| 阶段 | 动作 | 通过 |
|---|---|---|
| 1 静置零漂 | 平放静置 30 s | `gyro` 每轴绝对值 < 0.05 rad/s |
| 2 翻转重力 | 正立 → 倒立 | `gravity` 的 z 变号，模长始终 ≈ 1 |
| 3 方向检查 | 缓慢低头 | gyro 的 **Y 轴符号**与躯干约定一致 |
| 4 四元数连续 | 慢转 90° | 无跳变、模长 ≈ 1 |
| 5 读取稳定 | 50 Hz 连读 10 min | "与上一帧完全相同"的 stale 连续 ≤ 3，且不到 `IMU_FROZEN_RUN=25` |

阶段 3 不过时，**改 mount 四元数，不要改符号表**。任何一步不过，先查接线和轴向，
不要靠"软件里乘个 −1"糊弄过去——那会把一个装反的模块变成一个装反的模块**加一段说不清的代码**。

⚠️ 这里有一个 I²C 直读独有的坑：**不能凭模块丝印推断轴向**。LQ 这类载板的丝印描述的是
**板**的丝印方向，不一定是**芯片坐标系**的方向，而 mount 补偿的是后者。先用三轴分别
旋转实测出模块的传感器轴，再谈四元数。

**保存**：中控"IMU 安装核对"面板勾选已固定并核对方向 → 填四个数 → 保存安装确认。
校验规则（`console/service_control.py:131-135` + `feetech_commissioning.rs:581-607`）：

- `confirmed` 必须为真，否则拒："请先核对机身安装方向"；
- `mount_wxyz` 必须**恰好四个值**，每个落在 `[-1, 1]`，且 **`|‖q‖ − 1| ≤ 1e-6`（单位长度）**。
  这条不只中控校验：`Calibration::validate()`（`duck-control/src/feetech.rs:868-873`）在
  `robotd` 启动读标定文件时以同样容差再查一次，不合格直接 `configuration_error` 开不了总线——
  手改 TOML 时"差一点点没关系"是行不通的；
- 通过后写入 `imu_mount_verified = true`，并把**当前运行时的 `imu_source` 同步写进标定文件**
  ——这是防止"来源换了、四元数还是上一个来源的"那道闸；
- **同时强制 `motion_enabled = false`**。这不是回退，是设计：来源或朝向一变，之前所有
  关于姿态的承诺都作废，必须重新确认。所以 `verify-imu` 之后需要重新使能运动，不要以为卡住了。

## 8. H7：让 IMU 和舵机一起标定（顺序与仲裁）

"一起标定"**不是同时调**，而是让它们**互相验证**。做法是双向的，两个方向都过才算通过。

**为什么顺序必须是先舵机（H5）后 IMU（H6），再联合（H7）**：IMU 告诉你"躯干朝哪儿"，
舵机读数告诉你"关节在哪儿"，而"躯干姿态 + 关节角 = 头部/相机在世界里的朝向"这条等式两边
都可能是错的。如果你先调 mount，你会用错误的关节零位去凑一个错误的四元数——两个错误互相
掩盖，之后谁都查不出来。所以：**H5 的零位一旦确认就锁死，H6/H7 不再动它。**

### 正向核对：FK → IMU

躯干固定正立（或已知姿态），逐个关节单独驱动到已知角度，比较：

- 运动学正解给出的躯干系姿态变化（`robot.state.frames` / `kinematics` 的
  `head_imu_in_trunk()`，主仓 `kinematics/src/head.rs:97`）；
- IMU 四元数的实际增量（H4 的界面正在显示它）。

**判据：偏差 < ±2°**（清单 §5 定的口径）。三个单轴测试都要符号一致。

### 反向核对：IMU → 关节残差

这一步才是"联合"的价值所在：用 IMU 当量具，反过来检查每个关节的 `zero_raw` 和 `direction`。
把躯干刚性固定在正立，依次把单个关节移动到已知角度，用 IMU 的姿态增量反解该关节的零位残差。

**仲裁规则**（写在这里，因为这是唯一能区分两类错误的方法）：

> 残差 > ±2°，且**同一关节在任何躯干初始姿态下残差都一致** → 判为**舵机零位错**，回 H5 重测；
> 残差 > ±2°，但**误差方向随躯干姿态改变** → 判为 **mount 四元数错**，回 H6 重测。

零位错是"加一个常数"，mount 错是"转一个坐标系"。前者不随初始姿态变，后者一定变。分不清时
多做一次初始姿态（比如整机侧倾 15° 再跑一遍），不要靠猜。

### 端到端粗筛：倾侧与摔倒预测

`duck-control/src/fall.rs:105-111` 用
`ġz = −(ωx·gy − ωy·gx)` 外推约 0.3 s 后的重力方向，阈值 `tilt_z = −0.90`（≈距站立 26°）
且需要 `ġz > 0`（正在倒下，不是恢复）。

向**前、后、左、右**各匀速倾侧一次，检查：预测方向与真实倾侧方向一致，触发点落在 26° ± 8°。

这一项最省事的用处是**粗筛装反**：mount 差 90° 时符号会直接反过来，一测就露。它不能替代
前两个核对——它能证明"没装反 90°"，证明不了"没差 3°"。

## 9. H8：运动解锁

只有 H5 全部 `calibrated` + H6 `imu_mount_verified=true` + H7 双向 < ±2° 全部成立，
才允许把 `motion_enabled` 置 true。**顺序不可交换，任何一项缺失都不要"先开了试试"。**

解锁后逐级来，每级都要有"断电开关在手边、舵机温度、电源电压、通信错误数、机械干涉"五项记录：

1. 整机悬空，只读 10 min；
2. 悬空 + 扭矩，仅保持当前姿态，不加载策略；
3. 单关节小角度阶跃，逐个测；
4. 一条腿 5 只，手动全行程；
5. 软垫上静态站立；
6. 手扶小步态；
7. 最后才加载这条链路自己训练出来的 ONNX。

故障时的行为请当作硬约束来看：状态字非零、电压离开窗口、过温或接近堵转，后端会把该舵机
标成故障、**立即撤销策略使能并写入扭矩关闭，且在本进程内锁存**，再次 `robot.init` 也不会恢复。
处理顺序只能是：断电 → 查机械卡住与供电 → 重启进程。**不要在故障锁存时反复发运动命令。**

也不要在两处给出不同的门槛。

只留一条和 H5–H7 直接相关的提醒：**标定改过就要重烘仿真**。零位、方向、限位、mount 四元数
任何一个变了，而仿真里还是旧值，那 sim-to-real 的差距会被当成"策略没训好"去查，白跑几晚。

## 11. 红线

- **未过 H7 不开 `motion_enabled`。**
- **不复制任何样例 `zero_raw`。** 同 CAD、同 ID、同舵机也不能共用。
- **不在 I²C 直读时用总线网桥的 mount。** `imu_source` 与标定不同源会被 robotd 拒绝，那是保护。
- **不为了配置能启动而先填满 `calibrated`。** 未测的就写未测。
- **不在标定时同时开 Studio 的 URT2 调试台。** 一条总线一个主站。
- **不做加计/陀螺零偏标定。** 融合与零偏估计在芯片 SFLP 里；这件事在设计文档 §8 里是**明确延后**。
- **不接受非单位长度的四元数**，也不要"归一化一下就行"——四个数是你测出来的，和 1 差得远
  说明测的东西不对。

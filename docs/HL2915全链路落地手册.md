# HL-2915-C001 全链路落地手册

这份手册把“买了两只舵机”之后的工作拆成可以验收的小门槛：

```text
两只舵机台架
  → Radxa 串口和供电
  → HAT/IMU 单独验证
  → HL-2915 + IMU 混合总线
  → 相机和 HAT 外设
  → MJCF/执行器参数
  → 仿真 smoke test
  → 训练与 ONNX 导出
  → 吊装真机
```

不要把“程序能编译”当成“机器人能走”。每一层都有自己的通过条件；上一层没有通过，就不进入下一层。

## 1. 先看当前真实状态

### 已经在仓库里

- `duck-control/src/hl2915.rs`：HL-2915 的 Feetech 协议 v1 台架封装。
- `duck-control/src/bin/hl2915_probe.rs`：Ping、读状态、改 ID、显式回中、连续只读。
- `duck-control/src/imu.rs`：`imu_to_dxl` v2 的 12 字节 SFLP 解码和就绪门槛。
- `duck-control/src/bus.rs`：当前 XL330 + IMU 的 Dynamixel Protocol 2 总线实现。
- `scripts/setup-board.sh`：Radxa UART、设备树和系统依赖准备。
- `scripts/setup-gstreamer.sh`、`docs/project/media-bringup.md`：相机、MPP、GStreamer、WebRTC。
- `tools/microduck_learning/`、`docs/进阶学习文档-训练仿真与部署.md`：训练 smoke test、TensorBoard、ONNX 部署说明。

### 还不能宣称完成

- 当前仓库没有真实 HL-2915、HAT、IMU 和相机的现场测试结果。
- HL-2915 目前没有接入 `robotd` 的 `RobotIo`；不能直接替换 `bus.rs` 的 XL330。
- HL-2915 是 Feetech 协议 v1，现有 IMU 总线代码是 Dynamixel Protocol 2；两者混接前必须完成混合协议台架测试。
- 训练仓库 `microduck_rl`、HAT 原理图、完整 CAD 资料不在本仓库，需要单独准备并固定 commit。

## 3. S0–S3：两只舵机

HL-2915-C001 的官方资料、协议和内存表在[新手文档第 12 节](新手学习文档.md#12-已确定使用-hl-2915-c001-时的复刻路线)。

### 接线原则

```text
12 V 限流电源 ──保险丝/急停──┬── 舵机 Vcc
                             └── 调试器 Vcc（仅当调试器要求）
电源 GND ────────────────────── 舵机 GND + 调试器 GND
调试器半双工 TTL ─────────────── 舵机 Signal
```

Radxa、Pi 2、ESP32 不参与第一次舵机上电。两只出厂 ID 往往相同，第一次只能接一只。

### 命令顺序

```powershell
cargo test -p duck-control --all-targets
cargo check -p duck-control --bin hl2915_probe
cargo run -p duck-control --bin hl2915_probe -- COM3 1
cargo run -p duck-control --bin hl2915_probe -- COM3 1 --set-id 2
cargo run -p duck-control --bin hl2915_probe -- COM3 2
cargo run -p duck-control --bin hl2915_probe -- COM3 1 2
cargo run -p duck-control --bin hl2915_probe -- COM3 1 2 --watch-seconds 600
```

`--set-id` 是唯一会写 EEPROM 的普通选项；`--move-center` 需要输出轴卸载并确认机械安全后才能使用。

通过 S3 后保存一份实验记录：日期、舵机序列号、ID、最低电压、最高温度、读错误数、供电限流值。

## 4. S4：Radxa Zero 3W

### 4.1 先确认系统，不要接电机

```bash
uname -m
uname -a
ls -l /dev/ttyS2 /dev/ttyUSB0 /dev/ttyACM0 2>/dev/null || true
systemctl status serial-getty@ttyS2.service --no-pager || true
```

项目默认总线是 `/dev/ttyS2`；如果 `serial-getty@ttyS2` 正在运行，先停掉它，否则登录终端会抢总线。

### 4.2 安装板级环境

在目标板执行仓库的板级脚本，不要把它们当成普通 PC 安装脚本：

```bash
sudo sh scripts/setup-board.sh
sudo sh scripts/setup-gstreamer.sh
sudo sh scripts/setup-npu.sh
```

脚本会报告是否需要重启。修改设备树后才重启；不要在每一次重试时盲目重启。

### 4.3 在 Radxa 上跑两只台架程序

```bash
cargo test -p duck-control hl2915
cargo build --release -p duck-control --bin hl2915_probe
./target/release/hl2915_probe /dev/ttyUSB0 1 2 --watch-seconds 600
```

如果调试器直接挂到 Radxa 的 UART，设备名可能是 `/dev/ttyS2`；以 `ls /dev/tty*` 和设备树配置为准，不要凭猜测修改 `robotd.toml`。

## 5. S5：HAT 和 IMU

### 5.1 先把两类协议分开理解

当前 XL330 路线是：

```text
Radxa UART → Dynamixel Protocol 2 → XL330 + ID 200 的 IMU 转接板
```

HL-2915 路线是：

```text
Radxa UART → Feetech 协议 v1 → HL-2915
```

它们都可能使用 1 Mbps、单线半双工 TTL，但“波特率相同”不代表“协议相同”。在没有混合协议测试前，不能把 HL-2915 和现有 IMU 直接并到同一条线上后启动 `robotd`。

### 5.2 IMU 单独验收

先用现有 XL330/IMU 线路验证 HAT 和 IMU，不要同时引入 HL-2915：

```bash
ls -l /dev/ttyS2
sudo systemctl stop robotd mediad 2>/dev/null || true
sudo systemctl stop serial-getty@ttyS2.service 2>/dev/null || true
```

然后使用仓库已有的 `robotd` 只读路径，确认：

- ID 200 能回答；
- 连续读取 12 字节 IMU block；
- 约 25 个有效四元数样本后 `imu_ready` 才变为真；
- IMU block 不长时间完全重复；
- `robotctl health` 中没有 stale IMU 增长。

`SflpDecoder` 的默认安装旋转是代码中的 `DEFAULT_MOUNT`；如果实体 HAT 安装方向不同，必须记录新四元数安装旋转，不能通过“把 roll/pitch 符号改到看起来顺眼”来校准。

### 5.3 混合协议实现前的硬件门槛

要让 HL-2915 和 ID 200 的 IMU 同时工作，需要：

1. 一个真正支持半双工方向切换的转接电路；
2. 一个共享串口句柄、分别调用 Feetech v1 和 Dynamixel v2 的总线层；
3. 明确每次 tick 的事务顺序和超时；
4. 在两只舵机 + IMU 的台架上连续读写；
5. 才能把 `Feetech2915Io` 接进 `RobotIo`。

在这之前，`hl2915_probe` 和现有 `DynamixelIo` 必须分开使用。不要让两个进程同时打开 `/dev/ttyS2`。

## 6. S6：相机、HAT 外设和 WebRTC

相机链路不是“插上 USB 摄像头就完事”，Radxa Zero 3W 需要正确的 CSI 设备树 overlay、vendor kernel、ISP、MPP 和 GStreamer 插件。完整实测记录在[相机 bring-up](project/media-bringup.md)。

### 验收顺序

```bash
uname -a
ls -l /dev/video* /dev/mpp_service /dev/rga 2>/dev/null || true
gst-inspect-1.0 rkisp 2>/dev/null || true
gst-inspect-1.0 mpph264enc 2>/dev/null || true
gst-inspect-1.0 webrtcsink 2>/dev/null || true
```

只有在 `/dev/video*` 和 `rkisp_mainpath` 出现后，才开始调 GStreamer；只有 `mpph264enc` 和 `webrtcsink` 都能被当前 `GST_PLUGIN_PATH` 找到后，才测试 WebRTC。

相机无效时先看 overlay 和 kernel，不要先改 Rust pipeline。相机程序的控制权在 `mediad`，不要让 `robotd` 直接打开摄像头。

## 7. S7：仿真、MJCF 和模型重训

### 7.1 先跑现成模型

训练前先确认外部训练仓库存在并固定 commit：

```bash
git clone https://github.com/pollen-robotics/microduck_rl
cd microduck_rl
uv sync
uv run scripts/infer_policy.py --walking ../microduck/policies/alpha_walking.onnx --new-cmd-obs
```

如果本地没有 `microduck_rl`，就把训练阶段标为“未开始”，不要使用本仓库里的旧实验记录冒充当前结果。

### 7.2 HL-2915 不能直接使用 XL330 的执行器模型

至少要重新测量：空载速度和加减速、目标位置到实际位置的延迟、正反向回差、额定负载下电流和温升、供电电压下陷、关节安装后的摩擦和机械限位。

每个数字都要保存原始日志。然后才修改 MJCF 中的执行器质量、惯量、限位、速度、力矩、摩擦、回差和延迟。

### 7.3 训练四步

```bash
uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 4096
uv run play Mjlab-Velocity-Flat-MicroDuck --wandb-run-path <run>
uv run scripts/export.py Mjlab-Velocity-Flat-MicroDuck --wandb-run-path <run>
uv run scripts/infer_policy.py --walking <exported.onnx>
```

每次实验记录 commit、执行器参数、环境数量、迭代数、checkpoint、ONNX 文件、观测/动作形状和失败原因。5 次 smoke test 只能证明训练管线能 step，不能证明策略会走。

部署前必须保持：

```text
observation: [1, 61]
action:      [1, 14]
loop:        50 Hz
```

## 8. S8：从两只到整机

不要从两只直接跳到 15 只。顺序应是：

1. 两只悬空，只读 10 分钟；
2. 两只低速回中，记录温升；
3. 3 只组成一条腿，手动测试全行程；
4. 一条腿悬空，读位置/速度/负载/电流；
5. 两条腿 10 只，再加头部 5 只；
6. 15 只全总线只读；
7. 15 只悬空扭矩；
8. 软垫静态站立；
9. 手扶小步态；
10. 最后才加载重训 ONNX。

每一级都要有“断电开关在手边、舵机温度、电源电压、通信错误数、机械干涉”五项记录。

## 9. 你现在的下一步

现在只做这三件事：

1. 用 `hl2915_probe` 给两只舵机分配 ID=1 和 ID=2；
2. 运行 `--watch-seconds 600`，把输出和接线照片保存下来；
3. 记录转接器型号、Radxa 系统镜像、HAT/IMU 是否已经有实物、相机型号和训练仓库路径。

拿到这些信息后，下一步才是写混合协议 `RobotIo`，而不是提前把 XL330 的 `bus.rs` 改成一个未经实测的“兼容版”。

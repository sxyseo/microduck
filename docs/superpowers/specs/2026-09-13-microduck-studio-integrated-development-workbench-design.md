# Microduck Studio 集成开发工作台设计

**日期：** 2026-09-13  
**状态：** 已批准  
**目标：** 将硬件检测与分阶段调试、模型训练与续训、可视化调试和数据可视化整合进现有 Microduck Studio，降低软硬件调试成本和首次上手难度。

## 1. 已确认的产品边界

- 保持个人优先、本地优先，沿用现有 FastAPI、SQLite、静态网页和已有脚本。
- 训练统一支持本机 WSL2/Linux 与远程 GPU；首个闭环先打通本机，再复用同一任务协议接入远程执行。
- 训练与续训只运行工作台内置的受控配方和经过校验的参数，不开放任意 Shell 命令。
- 续训必须明确选择 checkpoint，并校验代码、配置、硬件契约和父训练血缘，禁止自动选择“最新 checkpoint”。
- 首版可视化覆盖硬件实时遥测、日志时间线、训练曲线和实验对比；3D 仿真回放后置。
- 一个响应式网页同时服务 PC、平板和手机，不分别开发原生客户端。
- 手机端默认允许查看、告警和安全中止，不允许直接启动硬件运动或写入舵机配置。
- 不引入 Redis、消息队列、微服务或通用插件系统。

## 2. 总体架构

Microduck Studio 继续作为单一控制面：浏览器调用本机 FastAPI，FastAPI 使用 SQLite 保存项目、硬件档案、任务、运行和产物，并通过独立进程调用现有硬件与训练工具。

执行位置由受控执行目标决定：

- `local`：直接在 Linux/macOS 或工作台所在的 WSL2/Linux 环境执行。
- `wsl`：从 Windows 调用明确发行版中的固定训练入口。
- `ssh`：通过固定 SSH 参数在远程 GPU 主机执行同一训练配方。

执行目标只改变命令的承载位置，不改变任务状态、日志、指标、产物和血缘格式。浏览器不直接访问串口或 SSH，也不进入实时控制环；整机总线继续由 `robotd` 独占。

## 3. 分阶段硬件能力

硬件档案从“整机是否完整”扩展为部件状态与能力集合。部件状态采用：

- `planned`：计划购买；
- `owned`：已到货；
- `installed`：已安装；
- `detected`：已由工具检测；
- `verified`：已按当前规则验收；
- `failed`：本阶段存在异常。

首版能力包含主控、单舵机台架、关节组、IMU、摄像头和整机。任务前置条件依赖能力，不依赖固定采购套餐。用户只购买部分硬件时，仍可执行并完成当前能力范围内的调试。

新增或更换部件只让依赖其物理契约的下游证据失效。HL-1910、HL-2915 等型号使用各自适配器、参数约束和规则版本，不能自动互换。

## 4. 统一任务生命周期

所有硬件检测、测试、训练、续训和分析采用统一状态：

- `pending`
- `checking`
- `running`
- `passed`
- `failed`
- `insufficient_evidence`
- `interrupted`

统一流程为：

`前置检查 → 参数确认 → 独立进程执行 → 日志/指标采集 → 规则判定 → 产物登记 → 下一步建议`

每次运行至少保存：任务种类、受控配方、执行目标、参数、生效配置、硬件档案、代码版本、父运行或 checkpoint、开始和结束时间、退出状态、结构化判定、日志摘要及产物校验值。

网页关闭不影响独立进程。服务重启后，无法证明仍由工作台管理的遗留任务标记为 `interrupted`，不能恢复为通过。硬件运动任务断线后禁止自动续跑；失败任务也不能自动重试运动。

## 5. 硬件检测与分阶段调试

硬件中心复用现有串口枚举、HL-2915 探针、连续测试、BAM 采样、主控 SSH 诊断和 IMU 工具，通过型号适配器提供受控计划。

每个阶段显示：适用硬件、接线和安全前提、只读检查、可选受限动作、实时指标、验收规则、失败原因及下一项检查。缺失的电压、电流、温度等值显示“不可用”，不能填零。

只读检查可批量运行；配置写入必须显示修改前后值并保留原值；产生运动必须绑定设备与会话、显式确认并具备已验证的停止手段。

## 6. 训练与续训

训练中心采用受控配方。配方声明允许的参数、入口程序、输出目录规则、预期指标和产物，不接受用户拼接命令文本。

训练计划至少包含：

- 执行目标和训练 checkout；
- Git commit、分支和已跟踪工作树状态；
- 环境/任务配置及其校验值；
- 执行器模型、观测动作契约、随机种子；
- 资源参数和产物目录。

续训在此基础上要求显式 checkpoint，并保存 `parent_run_id`、checkpoint 路径与 SHA-256。代码、环境配置、观测动作契约、执行器模型或硬件契约不兼容时停止在前置检查，不启动训练。

本机与远程任务输出统一的结构化事件流。取消训练时先请求子进程正常退出，再执行进程组终止；取消结果为 `interrupted`，保留最后已完整写入的 checkpoint，但不将其自动标为可部署策略。

## 7. 可视化调试与数据可视化

首版工作页面包含：

- 硬件指标：位置、电压、电流、温度、响应延迟、丢包和设备错误；
- 训练指标：奖励、损失、步数、吞吐、资源占用和 checkpoint 事件；
- 统一时间线：日志、参数变更、断连、告警、保存 checkpoint 和任务状态；
- 实验对比：选择两次运行，对齐配置变化、指标曲线和最终判定；
- 证据入口：从异常指标或日志跳转到对应运行、产物和问题记录。

首版使用已有 TensorBoard 数据分析工具和浏览器原生 SVG/Canvas 能力，不引入新的图表依赖。实时更新采用轮询增量事件；只有实际采样频率和连接规模证明轮询不足时才引入 WebSocket。

## 8. 配置与多端交互

配置按 `系统默认 → 硬件型号 → 项目 → 单次任务` 合并，并在运行记录中保存最终生效值。首版可配置硬件阶段、执行目标、训练配方参数、可见指标、告警阈值和报告内容。

布局使用同一响应式页面：

- PC 为三栏工作台；
- 平板为双栏；
- 手机为单栏卡片，优先展示进度、告警、曲线、日志、报告和中止操作。

配置项必须有服务端校验；隐藏控件不构成安全边界。移动端提交硬件运动或配置写入请求时，服务端仍拒绝缺少本机确认令牌的请求。

## 9. 错误处理与证据可信度

- 进程启动失败、超时、退出码异常、日志损坏、数据缺失和产物缺失分别记录。
- 运行显示状态与服务端判定使用同一结构化结果，不能解析脚本打印的 `PASS` 作为唯一证据。
- 远程断连不等于远程任务失败；在无法确认状态时标记证据不足，要求重新同步状态。
- 训练产物、checkpoint 和报告均保存 SHA-256；文件被替换或删除后显示为变更或缺失。
- 自动诊断只给出当前事实、可能原因、缺失证据和下一项检查，不自动修改参数、驱动硬件或启动付费训练。

## 10. 实施子项目与验收

### A. 统一任务与硬件能力模型

- 部件状态能独立保存和读取。
- 当前硬件能力决定可执行任务，缺少可选部件不阻塞无关流程。
- 服务重启、取消和异常退出的状态不误报成功。

### B. 硬件检测中心

- 现有探针、主控诊断和台架测试从统一入口启动并记录。
- 不同型号使用独立适配参数；不存在匹配适配器时只能执行通用只读检测。
- 模拟设备与真实硬件证据严格区分。

### C. 训练与续训中心

- 本机 WSL2/Linux 可运行受控训练配方。
- 续训必须明确 checkpoint，并能拒绝不兼容血缘。
- 远程 GPU 复用相同任务与产物格式。

### D. 可视化与响应式工作台

- 硬件与训练指标可按时间查看，日志事件能对齐。
- 两次运行可以比较配置和指标。
- PC、平板和手机布局均可用；移动端危险操作由服务端拒绝。

验证分为单元/接口测试、模拟设备和模拟训练测试、进程中断恢复测试、响应式界面检查，以及单独记录的真实硬件验收。软件与模拟结果不能替代真实硬件证据。

## 11. 暂不实施

- 3D 仿真回放与场景编辑器；
- 通用 Shell 终端；
- Redis、消息队列和微服务；
- 原生移动应用；
- 自动硬件采购；
- AI 自动调参、自动运动或自动付费训练。

这些能力只有在核心闭环的真实使用数据证明必要时再单独设计。

# Microduck 代码解释与使用教程（小白版）

这份文档回答三个问题：

1. 这个仓库整体在做什么？
2. 一条“让鸭子走路”的请求，代码经过哪些文件？
3. 我想改参数、换策略、加功能时，应该从哪里下手？

它不是逐行翻译源码，而是先画出地图，再沿着一条真实请求读代码。代码中的名称保持原样，方便你用编辑器搜索。

## 0. 先记住三句话

- 这是一个 **Rust workspace**，不是一个只有一个 `main.rs` 的小程序；每个目录通常是一个 crate（可以理解为一个独立的 Rust 子项目）。
- `robotd` 是唯一可以直接控制 15 个舵机和 IMU 的进程。手柄、手机、命令行都只能发送“意图”，不能绕过安全层直接写电机。
- ONNX 策略不是本仓库训练出来的。训练在相邻的 `microduck_rl` 项目完成，本仓库负责加载、执行和保护它。

## 1. 第一次运行：没有真机也能学习

### 1.1 工具链

根目录 `Cargo.toml` 写明了：

- Rust edition：2024；
- 最低 Rust：1.89；
- 主要依赖：`serde`/`serde_json`（数据和 IPC）、`tokio`（异步等待）、`clap`（命令行）、`ort`（ONNX Runtime）。

先确认版本：

```bash
rustc --version
cargo --version
```

如果版本低于 1.89，先升级 Rust 工具链。低版本会在依赖解析阶段报错，这不是项目逻辑错误。

### 1.2 先跑一个不需要硬件的测试

```bash
cargo test -p duck-control --lib
```

这组测试覆盖总线、IMU、观测拼装、策略校验和安全层；它不需要真的接舵机。当前控制库在本机已验证 74 个库测试和 3 个 BAM 记录器测试通过；另有 `imu_probe`、`hl2915_probe`、`hl2915_mixed_probe`、`hl2915_record` 和会受限运动的 `hl2915_bam_record` 五个台架入口。

再看主程序有哪些选项：

```bash
cargo run -p robotd -- --help
```

常用的离板参数是：

```bash
cargo run -p robotd -- --fake --no-policy --socket /tmp/robotd.sock
```

`--fake` 使用 `duck_control::FakeIo`，`--no-policy` 不加载 ONNX。它只验证“进程、控制循环和 IPC 能否启动”，不是物理仿真，也不会让电脑上的鸭子真的走起来。Unix socket 这条路径适合 Linux/macOS；Windows 可以先运行测试、查看帮助和阅读代码。

完整检查通常是：

```bash
cargo fmt --all
cargo test --workspace
```

`btd`、`configd`、`mediad` 等部分功能依赖 Linux 的 BlueZ、NetworkManager、GStreamer 或 I²C。笔记本上完整工作区测试失败时，先看报错是不是系统依赖，而不是马上修改 Rust 代码。

## 2. 项目地图：每个目录负责什么

根目录的 `Cargo.toml` 是工作区清单。下面按“新手理解”而不是按字母排序：

| 目录 | 作用 | 先看什么 |
|---|---|---|
| `robotd/` | 主控制守护进程：50 Hz 控制循环、状态、IPC | `src/main.rs`、`src/control.rs`、`src/intents.rs` |
| `duck-control/` | 控制核心：关节模型、总线、IMU、观测、ONNX、限幅 | `src/model.rs`、`bus.rs`、`obs.rs`、`policy.rs`、`safety.rs` |
| `duck-ipc-proto/` | 所有服务共用的 JSON-RPC 类型和方法名 | `src/lib.rs` |
| `robotd-params/` | `robotd.toml` 的字段、默认值、校验和编辑模型 | `src/registry.rs`、`src/lib.rs` |
| `robotctl/` | 机器人本机命令行：健康、配置、策略、更新 | `src/main.rs` |
| `duckctl/` | 开发者电脑上的 Bluetooth 客户端，不随机器人发布 | `src/main.rs` |
| `padd/` | 读取手柄，把按钮和摇杆变成机器人意图 | `src/pad.rs`、`src/main.rs` |
| `configd/` | Wi-Fi、设备名称、配对 PIN、手柄绑定 | `src/main.rs`、`src/net.rs` |
| `updater/` | 下载、验签、切换 release、健康门和回滚 | `src/engine.rs`、`src/verify.rs`、`src/reconcile.rs` |
| `mediad/` | 相机、音频、WebRTC 和远程入口 | `src/pipeline.rs`、`src/route.rs` |
| `tof/` | 头部 ToF 深度传感器和 `tofd` | `src/sensor.rs`、`src/main.rs` |
| `kinematics/` | MJCF 模型、头部/手部运动学 | `src/lib.rs`、`src/head.rs` |
| `odometry/` | 根据脚接触和 IMU 估计位移 | `src/lib.rs` |
| `scripts/` | 板卡安装、交叉编译、开发推送、系统测试 | `dev-push.sh`、`provision.sh` |
| `deploy/` | 板卡上的默认配置、systemd 单元、信任密钥 | `robotd.toml`、`updater.toml` |
| `xtask/` | 打包、签名、发布等开发工具 | `src/main.rs` |

### 2.1 服务之间怎么说话

```text
手柄 ──► padd ─────┐
手机 ───► btd ─────┤
命令行 ► robotctl ─┤  JSON-RPC 2.0 / 每行一个 JSON / Unix socket
                   ▼
                 robotd ──► 15 个舵机 + IMU
                   │
                   ├──► kinematics / odometry
                   └──► safety

configd：网络、身份和配对
updaterd：下载、验签、切换和回滚
mediad：相机、音频和 WebRTC
tofd：深度传感器数据
```

`duck-ipc-proto` 是这张图中间的“合同”。服务不共享彼此的内部实现，只共享请求、响应和状态类型。控制面使用 JSON-RPC/NDJSON；视频帧等大数据走媒体管线，不塞进控制 socket。

## 3. 一次“让它走”的请求经过哪里

下面以“手柄前推”为例。读代码时按这个顺序跳转，最不容易迷路。

### 第一步：输入变成意图

`padd` 读取手柄，把速度、头部角度、按钮等转换成 `robot.*` 调用。`robotd/src/intents.rs` 保存这些请求：速度和头部目标是“当前值”，技能和声音是“下一 tick 消费的一次性请求”。

这样设计的好处是：IPC 线程只写一个轻量的槽位，控制线程每个周期取一次；控制循环不会为了等手机、蓝牙或命令行而停下来。

### 第二步：`robotd` 启动两条路径

入口是 `robotd/src/main.rs::main`：

1. 解析命令行参数；
2. 从 `robotd-params` 加载 `/etc/robot/robotd.toml`（不存在时使用默认值）；
3. 创建 `RobotState` 和 `Intents`；
4. `spawn_control_thread` 启动独立控制线程；
5. `serve` 在 Unix socket 上接受 JSON-RPC 请求。

控制线程单独存在，是因为真实舵机总线读取是阻塞 I/O。它不能占用处理 IPC 的异步线程，也不能让一次慢的串口事务拖住命令行响应。

### 第三步：50 Hz 控制循环

`robotd/src/main.rs::control_loop` 每约 20 ms 做一次：

```text
读总线（舵机位置/电流/电压 + IMU）
        ↓
读取 Intents，得到速度、头部、身体姿态和技能
        ↓
duck-control::obs 组装 61 维 observation
        ↓
duck-control::policy 调 ONNX，得到 14 维 action
        ↓
duck-control::safety 检查死区、关节范围、IMU、失联和跌倒策略
        ↓
把目标写回 15 个舵机
        ↓
发布 RobotState，供 monitor/health/客户端读取
```

调度器使用 `MissedTickBehavior::Skip`：如果某次太慢，就丢掉过期 tick，不补发一串连续电机命令。对机器人来说，“保持当前节奏”比“把旧命令补完”更安全。

### 第四步：客户端看到状态

`robotd` 通过 `robot.subscribe` 推送状态。状态里会同时出现：

- 请求的速度和实际应用的速度；
- 哪个安全规则修改了命令；
- 15 个关节的当前位置和目标；
- IMU 重力方向与跌倒标记；
- 实际循环频率和丢 tick 数；
- 电池、温度和里程计。

因此排错时先看“请求”和“实际应用”是否不同，再决定是手柄、策略还是安全层的问题。

## 4. 最重要的契约：61 → 14

这是改造项目时最容易误伤、也最值得先理解的部分。

- 机器人有 15 个关节；
- 嘴的索引是 `MOUTH_INDEX = 9`，嘴不参与行走策略；
- 策略输入是 61 个观测值（`POLICY_OBS_LEN`）；
- 策略输出是 14 个动作（`POLICY_ACTION_LEN`）。

`duck-control/src/obs.rs` 负责把关节反馈、IMU、命令和身体姿态按固定顺序拼成 observation，也负责把 14 个 action 放回 15 个关节的位置。训练代码和运行时代码必须使用同一顺序；顺序错了通常不会触发 Rust 错误，只会让机器人动作异常。

`duck-control/src/policy.rs` 负责：

- 检查 ONNX 文件是否存在、能否加载；
- 检查输入/输出形状；
- 预热运行时；
- 把推理错误变成可报告的 `PolicyError`。

`duck-control/src/safety.rs` 是最后一道门：策略提出的是目标，不是命令。安全层会处理关节限位、非有限数值、deadman（长时间没有速度意图）和与跌倒相关的增益策略。

**不要为了“先让它动”而跳过 `safety`。** 安全层是设计的一部分，不是调试噪音。

## 5. 小白改造指南：先判断你要改哪一层

### 5.1 只想调参数或开关：不要先改 Rust

板上配置是 `/etc/robot/robotd.toml`，参考模板是 `deploy/robotd.toml`。推荐使用：

```bash
robotctl configure --list
sudo robotctl configure
```

常见配置位置：

| 想调整什么 | 配置位置 |
|---|---|
| 控制频率、输入平滑 | `[control]` |
| 使用 walk 还是 roller | `[policy] mode` |
| 是否加载策略、动作缩放、低通 | `[policy]` |
| deadman、跌倒和 limp gain | `[safety]` |
| 声音、宠物检测 | `[audio]` |
| ToF theremin | `[theremin]` |
| 相机和视频 | `[media]`，由 `mediad` 读取 |

配置通常在进程启动时读取；改完后按命令提示重启对应服务。配置位于 `/etc/robot`，不会随着 release 目录替换，所以更新后仍然保留。

### 5.2 想换一个行走策略：优先换 ONNX，不改控制环

官方或自制策略必须满足 `obs[1,61] -> actions[1,14]`。在真机上先查看当前策略：

```bash
robotctl policy list
```

尝试一个文件：

```bash
sudo robotctl policy load walk /home/radxa/my_walking.onnx
```

撤销覆盖：

```bash
sudo robotctl policy reset walk
```

这条路径会先校验新文件；加载失败时保留旧策略。第一次试验应让机器人离地或限制活动范围，并观察 `robotctl monitor`。

### 5.3 想添加一个一次性动作：使用 skill

“走路”是 slot；“踢球、翻滚、鞠躬”是 skill。添加 skill 不需要新写一个守护进程：

```bash
sudo robotctl policy add polite-bow /home/radxa/polite-bow.onnx
robotctl robot do polite-bow
```

技能配置最终写入 `[[policy.skill]]`。按钮绑定由 `padd` 每秒重新读取：

```bash
sudo robotctl pad bind x polite-bow
robotctl pad bindings
```

只有机器人正在驱动策略时才会执行 skill；这不是命令行忘了发，而是 `robotd` 有意拒绝了不安全的上下文。

### 5.4 想改硬件映射：从 `model.rs` 开始，别只改一个数字

关节名称、顺序、ID、方向和 home pose 集中在 `duck-control/src/model.rs`；总线读写和协议细节在 `duck-control/src/bus.rs`。修改硬件映射时必须同时检查：

1. `JOINT_NAMES`、`JOINT_IDS` 和 `MOUTH_INDEX`；
2. `obs.rs` 的索引是否仍然对应训练数据；
3. `bus.rs` 的寄存器、波特率和设备数量；
4. `model.rs`、`bus.rs`、`obs.rs`、`safety.rs` 的测试；
5. 断电、限流、单舵机台架，再到整机。

**不要**只把 `JOINT_IDS` 改成手上的 ID 就上电。ID 顺序就是软件和硬件的合同，错一位可能是“左腿当右腿”，而不是一个明显的编译错误。

### 5.5 想加一个新的客户端命令：沿着 IPC 合同走

推荐顺序：

1. 在 `duck-ipc-proto/src/lib.rs` 增加请求参数、结果类型和 `Call` 变体；
2. 在 `robotd/src/main.rs` 的路由/`dispatch` 中接住请求；
3. 如果命令会改变运动，写入 `robotd/src/intents.rs`，不要在 IPC 线程直接碰总线；
4. 在 `control_loop` 消费这个意图；
5. 在 `robotctl/src/main.rs` 或 `padd` 增加用户入口；
6. 为“正常、拒绝、控制循环未启动”各留一个最小测试；
7. 如果是兼容性变化，检查 `duck_ipc_proto::API_VERSION` 和所有客户端。

可以把这条规则概括为：**IPC 线程提出请求，控制线程决定何时执行，安全层决定能否执行。**

### 5.6 想改升级逻辑：只改 `updater`，不要让客户端绕过它

升级流程是：下载 → 验签 → 解包到新目录 → 切换 `current` → 重启服务 → 询问 `robot.health` → 健康则保留，否则回滚。重点文件：

- `updater/src/manifest.rs`：发布物描述；
- `updater/src/verify.rs`：签名和信任密钥；
- `updater/src/engine.rs`：主流程；
- `updater/src/reconcile.rs`：服务是否都跑在当前版本；
- `updater/src/faults.rs`：可注入的失败路径。

不要在 `robotctl` 里自行替换 `/opt/robot/daemon/current`。那会绕过验签、健康门和回滚，等于把项目最重要的恢复能力删掉。

## 6. 改代码前的阅读顺序

建议每次只沿一条链阅读：

1. `Cargo.toml`：确认 crate 和依赖边界；
2. `duck-ipc-proto/src/lib.rs`：确认请求和状态的外部形状；
3. `duck-control/src/model.rs`：确认机器人有哪些关节；
4. `duck-control/src/obs.rs`：确认训练和运行时如何对齐；
5. `duck-control/src/policy.rs`：确认模型如何加载；
6. `duck-control/src/safety.rs`：确认哪些命令会被修改或拒绝；
7. `robotd/src/intents.rs`：确认请求如何跨线程传递；
8. `robotd/src/main.rs::control_loop`：确认最终写入电机的地方；
9. `robotctl/src/main.rs`：确认用户命令怎样进入 IPC。

## 7. 一套最小改造闭环

假设你想把某个输入参数调小：

```text
先找到参数的所有读取点
  → 判断它是 robotd.toml 还是训练策略参数
  → 在 FakeIo/单元测试里验证
  → cargo fmt --all
  → cargo test -p 受影响的 crate
  → 再跑 cargo test --workspace
  → 有真机时先断开负载、低增益、限制活动范围
  → 用 robotctl monitor 对照“请求 vs 实际应用”
```

推荐的最小检查命令：

```bash
cargo fmt --all -- --check
cargo test -p duck-control --lib
cargo test -p robotd --bin robotd
cargo test --workspace
```

Linux 目标的代码还应按贡献指南检查：

```bash
RUSTFLAGS="-D warnings" cargo clippy \
  -p configd --all-targets --target aarch64-unknown-linux-gnu
```

## 8. 常见误区

### “`robotd --fake` 就是仿真器”

不是。它是无总线的 `FakeIo`，用来测试线程、状态和命令路径；完整物理仿真和策略训练在 `microduck_rl` / MuJoCo 一侧。

### “机器人不动，一定是策略坏了”

先看：

1. `robotctl health`：控制循环、总线、策略是否健康；
2. `robotctl monitor`：请求是否到达、是否被 `deadman` 或限位改写；
3. `robotctl policy list`：加载的是哪一个文件；
4. 日志：`journalctl -u robotd -b`。

### “把 61 改成 60 试试”

不要。观测宽度、动作数量和索引顺序是训练/部署合同。想改变它，需要同时改训练工程、ONNX 导出、manifest、运行时校验和测试。

### “直接编辑 release 目录里的默认配置”

不要。release 会被升级替换。每台机器的长期调整放在 `/etc/robot/robotd.toml`，策略覆盖用 `robotctl policy load`，这样更新和回滚仍然可控。

### “先把安全层注释掉”

不要在真机上这样做。调试时可用 `FakeIo`、低增益、离地台架和 `--no-policy` 缩小风险；安全层是最后一道防线。

## 9. 学完这篇后做什么

如果你是第一次接触 Rust/机器人，建议按这个顺序完成：

1. 跑通 `cargo test -p duck-control --lib`，并在 `obs.rs` 找到 61 维布局测试；
2. 阅读 `robotd/src/intents.rs`，解释“当前值”和“一次性请求”的区别；
3. 用 `robotd --help` 认识 `--fake`、`--no-policy`、`--params`；
4. 读 `deploy/robotd.toml`，只挑一个参数说明它影响哪个模块；
5. 再去看 `deep-dive/01`、`02`、`04`、`09`、`10`；
6. 最后才接真机、换策略或改硬件 ID。

一句话总结：**先沿着 `输入 → intents → 61 维观测 → ONNX → safety → 舵机` 读通一条链，再改对应层；不要从一个看起来顺眼的数字开始改。**
